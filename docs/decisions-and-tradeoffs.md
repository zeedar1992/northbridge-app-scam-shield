# Decisions and trade-offs

Each row says what I chose, what I rejected, and why. These are the questions a technical buyer (Head of Fraud Engineering / Enterprise Architect) asks.

| # | Decision | Alternatives considered | Why this choice | What I gave up / how I'd mitigate in production |
|---|---|---|---|---|
| 1 | **Lakeflow Spark Declarative Pipelines (SQL)** with Auto Loader for bronze→silver→gold | Hand-written Structured Streaming jobs; dbt on a warehouse; Lakeflow Connect | Declarative = lineage, expectations (DQ metrics), AUTO CDC de-dup and incremental file discovery for free; SQL is readable by the bank's data team. Lakeflow Connect is for SaaS/DB sources, but here the sources drop files. | Less control over micro-batch tuning. In production the payments hub would publish to Kafka / Zerobus; the bronze table changes from `read_files` to a Kafka source and nothing downstream changes. |
| 2 | **AUTO CDC (SCD1) on `payment_id`** to de-duplicate at-least-once deliveries | `dropDuplicates` with watermark; MERGE in a job | Idempotent and replay-safe, sequenced by ingestion time, no state-store tuning. | Slightly more storage (validated table and deduped table). Worth it for auditability. |
| 3 | **Quarantine table** instead of silently dropping bad rows | Expectations-only drop | Payments ops can see and fix the 2,886 rejected events; regulators expect no silent data loss. | One extra streaming table. |
| 4 | **UC column masks declared in pipeline DDL** (`MASK fn`) + governed tags (`class.*`, `data_classification`) | Separate secure views; masking in the app | Masks travel with the table into every consumer (Genie, notebooks, app SP, synced tables). ML features (age band, postcode district) are derived *inside* the governed pipeline, so nobody downstream needs raw PII. | Masks are evaluated per query (small overhead). Row filters (e.g. by region) were not added because synced tables to Lakebase do not support row-filtered sources; I'd use per-team views if needed. |
| 5 | **Existing catalog + `northbridge_*` schemas** | Dedicated catalog | No CREATE CATALOG privilege on the shared metastore. Schemas are bundle-managed with comments, properties and grants. | In a customer build: one catalog per domain/environment (`northbridge_fraud_prod`). |
| 6 | **LightGBM, value-weighted positives, time-based split** | Logistic regression; deep learning; AutoML; random split | Gradient boosting is the industry workhorse for tabular fraud. It is explainable via native SHAP contributions (`pred_contrib`), fast to serve on CPU, and handles nulls (e.g. "no receiving-bank intel"). Value weighting matches the business loss function (£ reimbursed, not counts). A time split avoids leakage. | No hyper-parameter sweep (time-boxed). Next step: Optuna sweep + MLflow, champion/challenger via UC aliases. |
| 7 | **Compare at the same alert budget** (K = rules alert volume) | Report AUC only | The fraud team's capacity is fixed, so the buyer's question is "more scam £ caught with the same team?" AUC doesn't answer that. | Real budget is set per day/shift. The threshold is stored in the model metadata and can be re-tuned without retraining. |
| 8 | **pyfunc wrapper returns score + band + reason codes** | Raw model + separate explainer | One artefact for batch, real-time and GenAI. Reason codes are required for analyst trust and for explaining holds to customers (Consumer Duty). | The wrapper is custom code; it's covered by the smoke test in `06_deploy_model_serving`. |
| 9 | **GenAI via `ai_query` in batch (Claude Haiku) + live calls in the app (Claude Sonnet)** | Agent framework / RAG; a single model | Batch enrichment pre-computes case notes for the whole queue (cheap, fast, governed in SQL). Sonnet is used only for interactive, higher-stakes customer wording. Structured JSON is parsed with `from_json`, and failures are recorded in `genai_error`, never fatal. | Prompt-based JSON (Claude endpoints reject `responseFormat` here). Mitigated by regex extraction + a typed schema. Next step: MLflow evaluation with Guidelines judges ("non-accusatory", "no leading questions"). |
| 10 | **Lakebase for the app, warehouse for analytics** | App reads Delta via the SQL warehouse; external Postgres | The analyst queue and the real-time check need single-row reads/writes, transactions (decision + status in one commit) and sub-10 ms lookups. A warehouse is built for scans. Lakebase is managed, scale-to-zero, governed by the same workspace identity, and syncs with UC both ways. | A second store to operate, mitigated by synced tables (no ETL code) and Lakehouse Sync (no CDC tooling). |
| 11 | **Synced tables: TRIGGERED for the alert queue, SNAPSHOT for profiles** | All CONTINUOUS | The queue changes incrementally (MERGE + CDF), so triggered sync is cheap. Profiles are fully recomputed each run, and snapshot is ~10x faster when >10% of rows change. Continuous would cost a pipeline running 24/7. | Up to one job cycle of staleness for profiles. Fine for daily baselines; production would run the job hourly. |
| 12 | **Lakehouse Sync (Lakebase → UC) for analyst decisions** | App writes to Delta directly; nightly export | Closes the loop with zero code: every decision becomes an SCD2 history row in UC. Genie can report on it, and it becomes fresh labels for retraining days before customer claims arrive. | Beta feature; the history table needs `REPLICA IDENTITY FULL` (set in DDL). |
| 13 | **Model Serving (CPU Small, scale-to-zero) + AI Gateway inference tables** | Score inside the app process | Independent scaling, versioned rollout via UC alias, every request logged to UC for monitoring/audit. | Cold start after scale-to-zero (~seconds). Production: min 1 replica during banking hours. |
| 14 | **Feature parity: app rebuilds the same features from Lakebase profiles** | Databricks Feature Store online tables | Fast to build and transparent (`backend.build_features` mirrors `03_gold.sql`). | Risk of training/serving skew. Production: Feature Engineering in UC with online feature serving (Lakebase-backed) and point-in-time lookups. |
| 15 | **Genie Agent over curated tables + a UC metric view, deployed as code** | Point Genie at the whole schema | Curated scope + instructions + example SQL + benchmarks = higher accuracy. The metric view gives one governed definition of "value recall", "net reimbursement cost". PII columns are excluded in the Genie config *and* masked in UC. | Needs maintenance as questions evolve, via the benchmark set in the JSON. |
| 16 | **FastAPI + dependency-free HTML/JS front end** | AppKit (React/TS); Streamlit | One Python codebase, with the SDK for every Databricks call and no Node build. The UI is still a proper four-view business app. Streamlit can't easily do a transactional queue UI. | Less component polish than AppKit. Would port to AppKit for production. |
| 17 | **Everything in one Declarative Automation Bundle + one Lakeflow Job DAG** | Click-ops; separate repos per stage | Reproducible, reviewable, promotable dev→prod. The job DAG makes the integrated journey explicit. | First deploy is two-phase: synced tables and the Genie space need tables the job creates. Documented in the README. |
| 18 | **Synthetic, scam-enriched data; business case applies measured *rates* to published UK baselines** | Extrapolate synthetic £ totals | The sample is enriched (~0.3% scam rate) so the model can learn. Extrapolating its totals would overstate value. Applying measured recall/precision uplift to UK Finance / PSR figures is honest and defensible. | Absolute rates on real data will differ. The proposal is a 6-week shadow-mode pilot on Northbridge's own history to re-measure before go-live. |
| 19 | **Batch scoring on the driver with the same pyfunc** (pandas, LightGBM `pred_contrib` for reason codes) | `mlflow.pyfunc.spark_udf` across serverless workers; score inside the SDP pipeline | Simplest correct path, and it's identical code to the real-time endpoint. Lesson learned in this build: TreeSHAP on all 1.1M payments was ~10^12 operations and did not finish, so reason codes are now computed only for MEDIUM+ scores (a small fraction of payments). | Production: `spark_udf` (distributed) or only compute contributions for MEDIUM+ scores. Both are easy changes because the model contract (signature) is explicit. |
| 20 | **Generous `max_tokens` (2,000) for Claude 5.5 + parse failures logged, not fatal** | Tight token budget for cost | Found during the build: Claude 5.5 endpoints reject `temperature`, and with `max_tokens=600` some responses were truncated mid-JSON (the model spends budget on reasoning), so `from_json` returned null. | Slightly higher token cost per case note. It's bounded by the 300-alert cap per run. |
